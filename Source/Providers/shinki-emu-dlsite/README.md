# DLsite PC download provider

Protocol research date: 2026-10-27. DLsite does not document a versioned download API. The links below pin maintained third-party implementations of authenticated store behavior; no account-owned responses or credentials are included here. All store endpoints use the existing workspace `reqwest` HTTP client. The provider downloads only original PC files belonging to the signed-in account; Play-optimized files are out of scope.

A Play purchase alone establishes Play access, not availability of a PC game installer. A missing PC download response is shown as unavailable in title detail; incomplete or unfamiliar listings return `StoreError::Metadata` rather than inventing a file URL. The Play optimized media `download/sign/cookie` and `ziptree.json` endpoints produce web-reader assets and are deliberately never used by the provider. [Play client, commit `addfcc8c`](https://github.com/bhrevol/dlsite-async/blob/addfcc8c2feff824e272e5509b0f642b32abc9cf/src/dlsite_async/play/api.py)

## File and update behavior

A single original `.zip` is extracted under the Manager-owned `.shinki/store/dlsite/<workno>/` staging directory with absolute-path, parent-traversal, Windows invalid-name, duplicate-entry, and symlink checks; only after successful extraction is it moved to the game install directory. `zip =9.1.0` is already used by the workspace Manager; this provider adds no HTTP stack. `.rar`, multi-volume `.partN.rar`, `.exe`, and self-extracting parts are downloaded with the server's filename and left unchanged in `dest`. A fixed `ManualExtractionRequired` notice tells the user to extract or run the official installer manually. The provider never executes installers or removes DRM/license checks. The maintained [archive downloader, commit `4087506`](https://github.com/AcrylicShrimp/dlsite-manager/blob/4087506a296a687fcc3b8cb814b8e51d17fca6a0/crates/dm-archive/src/lib.rs) demonstrates ZIP and legacy RAR handling but does **not** prove all DLsite `.exe` parts are extractable RAR; this provider never assumes so.

Downloaded part names and sizes are written to `installed-parts.json` under Manager-owned work storage, not into the game directory. The available endpoints do not supply a reliable original-installer build ID or revision comparable with an installed game; `has_update` returns `UpdateState::Unknown`, not an unsupported update guess based on product or purchase dates.

## Live verification requiring the user's DLsite account

1. Sign into DLsite in a browser and complete any CAPTCHA/2FA. Supply the browser cookies to the Manager's DLsite sign-in. Check that only the account's owned works appear; no credentials or tokens should be shared with developers.
2. Choose one account-owned single ZIP game, one split `.partN.rar`/`.partN.exe` game if owned, one serial-required game if owned, and one Play-only title. Confirm ZIP files land under the chosen install directory and split/SFX parts retain original filenames with the manual-install notice. Check interruption/resume, `Content-Range` consistency, size verification, and update state **Unknown**.
3. If the account's original-PC listing cannot be parsed, use browser developer tools on the **signed-in** download action and export a HAR **with response content**, from `https://play.dlsite.com/api/v3/download?workno=<owned work number>` through every redirect and `/home/download`, `/home/serial`, or split listing request. Before sharing, redact `Cookie`, `Set-Cookie`, auth headers, serial numbers, signed query parameters, and personal information. Never commit or log the raw HAR. Record the actual `Content-Disposition`, `Content-Length`, `Content-Range`, and checksum headers if available. These response shapes are **unverified** without the user's account.

No DRM bypass, cookie scraping from other applications, Play streaming extraction, or guessed installer endpoint is supported.
